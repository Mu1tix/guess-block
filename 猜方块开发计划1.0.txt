猜方块 开发计划 1.1
（由 1.0 讨论稿修订：锁定范围、三态答案、环境与维护方式）

一、项目概述

做一个猜 Minecraft 方块的 H5 网页游戏，核心类似「20 个问题」或 Akinator：
系统（或出题玩家）选定一个方块，其他玩家可以猜方块名，也可以用自然语言提问，系统（或出题者）用「是 / 否 / 不确定」回答。

一期目标：单人模式可玩 Demo。
二期目标：房间 + 合作模式，方便分享到 QQ 群。
三期目标：1vX 对抗模式、部署与兼容性打磨。

不做的事（一期明确不做）：
· 不做小程序
· 不做 LLM / GPT 自动问答
· 不自动给所有方块编造是/否（学习只记录玩家教过的方块）
· 不追求全版本、全图鉴
· 不使用 Mojang 官方贴图（用文字和色块即可）


二、已确定的产品规则（开发必须遵守）

1. 版本锁定
   · 方块数据以 Java Edition 1.20.1 为准
   · 页面上必须写明版本，避免和基岩版 / 其他版本对线

2. 方块范围
   · 一期约 100～150 个常见方块（原木、木板、石头、矿石、下界、功能方块等）
   · 新方块靠改数据文件追加，不改游戏规则

3. 输入分两种
   · 猜测：输入方块中文名、别名或英文 id（如「橡木原木」「glowstone」「萤石」）
   · 提问：自然语言是非问句（如「它是自然生成的吗？」）

4. 系统回答（三态，不能只做是/否）
   · 是
   · 否
   · 不确定（问题无法识别，或该属性在数据里缺失）
   · 猜测另有：正确 / 错误

5. 单人模式次数
   · 提问 15 次
   · 猜测 5 次
   · 猜中立即胜利
   · 猜测次数用尽则失败并公布谜底
   · 提问用尽后仍可继续猜，直到猜测用尽

6. 「自然生成」口径（避免扯皮）
   · 指作为地形 / 植物 / 矿物 / 维度环境生成
   · 不包括仅出现在村庄、要塞等建筑物里的装饰方块
   · 例：橡木原木 = 是；橡木木板 = 否（即使村庄里有）

7. 「可合成」口径
   · 指能在工作台（合成栏）作为产物得到
   · 熔炉烧炼、切石机不算「可合成」


三、三种游戏模式（分期）

· 单人模式（一期）：系统出题，本地自动回答。纯前端，可先不联网。
· 合作解谜（二期）：系统出题，多人共享次数，任何一人猜中即团队胜。
· 1vX 对抗（三期）：房主选方块，猜题者提问，房主手动点是/否；系统可提示属性防答错。


四、技术栈与开发环境（给零基础维护用）

这是网页项目，不需要 Visual Studio、JDK、C++ 编译器。

必装：
· Node.js LTS（https://nodejs.org），安装后自带 npm
· 编辑器：Cursor
· 浏览器：Chrome 或 Edge

常用命令（请优先用「命令提示符 CMD」，不要用被策略拦住的 PowerShell）：
· node -v          查看 Node 版本
· npm -v           查看 npm 版本
· npm install      第一次、或依赖变化后安装
· npm run dev      本地启动，浏览器打开终端提示的地址（一般是 http://localhost:5173）
· npm run build    打包，以后上线才用

若 PowerShell 报「禁止运行脚本」：
· 改用 CMD；或执行：
  Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned

项目结构（一期）：
· package.json          依赖与命令
· vite.config.js        开发服务器配置
· index.html            网页入口
· src/main.js           启动 Vue
· src/App.vue           单人游戏界面
· src/data/blocks.js    【你最常改】方块名单与属性
· src/data/taxonomy.js  学习系统的一级分类（外观、材质等）
· src/game/parser.js    把输入识别成「猜测」或「提问」
· src/game/engine.js    次数、胜负、历史记录
· src/game/learner.js   未识别问题 → 自动归类 + 局后教是/否
· src/game/wiki.js      查阅中文 Minecraft Wiki 并回写学习库
· src/game/unrecognized.js  完全拆不开的句子日志

二期才需要：
· 后端 Node.js + Express + Socket.IO
· 房间码、链接进房
· 部署：前端 Vercel / Netlify；后端 Railway / Render / 云服务器


五、方块数据字段（改 src/data/blocks.js 时按此复制）

每条方块包含：
· id            英文 id，唯一，如 oak_log
· name          中文官方名
· aliases       别名数组，如「萤石」可加「发光石」
· natural       是否自然生成（见上文口径）
· craftable     是否工作台可合成
· tool          最合适工具：none / pickaxe / axe / shovel / hoe / shears / any
· mineLevel     0 空手可挖有效；1 木；2 石；3 铁；4 钻石（如黑曜石）
· luminance     0～15，0 表示不发光
· transparent   是否透光 / 非完整遮挡
· flammable     是否可被火烧毁
· gravity       是否受重力（沙、砾石、铁砧）
· solid         是否固体
· fullCube      是否完整方块
· renewable     是否可再生
· redstone      是否红石相关（导电、元件、红石矿等）
· hasInventory  是否能装物品（箱子、熔炉、漏斗等）
· silkTouch     是否通常需要精准采集才能掉落自身（草方块、矿石玻璃等）
· blastResistant 是否明显防爆（黑曜石、基岩、下界合金块等）
· dimension     数组：overworld / nether / end（主要生成维度）
· category      数组：wood / log / planks / leaves / stone / ore / dirt / plant
                / fluid / nether / end / redstone / functional / decorative
                / metal_block / glass / wool / ice / light 等
· color         数组：主要观感颜色 red/orange/yellow/green/cyan/blue/purple/
                pink/white/black/gray/brown
· woodType      木材种类或 null：oak/spruce/birch/jungle/acacia/dark_oak/
                mangrove/cherry/bamboo/crimson/warped


六、提问解析与自动学习

采用关键词 + 规则，不调用大模型。

处理顺序：
1. 空输入忽略
2. 若整句能匹配某个方块名 / 别名 / id → 视为猜测
3. 若问句里点名某个方块（「它是萤石吗」）→ 视为猜测
4. 否则按内置规则表匹配属性（自然生成、发光、下界、木头、颜色等）
5. 仍匹配失败 → 先查中文 Minecraft Wiki（zh.minecraft.wiki 的 MediaWiki API）：
   · 用方块中文名 / 别名 / 英文 id 找条目（跟随重定向，如 萤石 → 荧石）
   · 读取条目导言与信息框（亮度、可再生、工具、固体、红石导体等）
   · 能从百科确定是/否 → 立刻写入本机学习库并回答，标注「来自 Minecraft Wiki」
   · 百科没把握 → 不编造，进入下一步
6. Wiki 也查不清 → 自动学习层接手：
   · 从问句抽出属性名（是/会/能/有/需要……吗）
   · 自动挂到分类树的某一层：外观 / 来源与维度 / 材质 / 采集方式 / 功能与交互 / 物理性质 / 未分类
   · 和已有学习属性相似则合并，不重复开类
   · 立刻回答「不确定」，并说明已归入哪一层
7. 本局谜底揭晓后，把仍未确定的新问题展示给玩家：只针对这个方块点「是 / 否 / 跳过」
8. 下次同一方块再被抽到、再问同类问题，就可以用已学习的是/否直接回答

硬性限制（防止把数据库学坏）：
· 系统可以自动新建分类层级
· Wiki 只在有明确依据时写入是/否（本方块），不推广到全部方块
· 查不清就说不确定，禁止瞎答
· 条目版权归 Wiki 作者，使用时需署名（CC BY-NC-SA）
· 开发环境通过 Vite 代理访问 Wiki，避免浏览器跨域；请做文明请求（缓存 7 天、超时 10 秒）

学习数据存在浏览器 localStorage，首页「知识库」可查看、导出 JSON、导入、清空。
导出文件可备份；以后若做服务器，再把这份 JSON 迁到后端。


七、开发路线

第一步（当前）：单人 Demo
· Vue 3 + Vite 纯前端
· 方块库 + 解析器 + 次数与胜负 + 手机优先界面
· 本地验证：问句覆盖率、别名、相似方块能否区分

第二步：后端与房间
· Node.js + Express + Socket.IO
· 创建 / 加入 / 离开房间，6 位房间码，链接 ?room=XXXXXX
· 单人逻辑迁到服务端，保证多人同一谜底
· Socket.IO 必须能降级到 HTTP 长轮询（QQ 内置浏览器）

第三步：合作模式
· 系统出题，共享提问/猜测次数
· 按房间串行处理提交，避免次数扣成负数

第四步：1vX 对抗
· 房主选题，猜题者提问，房主回答
· 房主端可显示属性提示，不向猜题者泄露谜底

第五步：分享与部署
· 一键复制带房间码的链接和分享文案
· HTTPS 部署，真机测试 QQ 内置浏览器
· 内存房间即可；重启会丢房间，页面需提示


八、后期维护（你一个人也能做的部分）

日常（改数据，不必懂 Vue）：
· 新方块：在 src/data/blocks.js 里复制一条，改 id/name/属性
· 玩家用了别的叫法：在 aliases 里加
· 系统经常「不确定」：先玩一局，结束时点是/否教它；或打开「知识库」看新分类是否挂对
· 学坏了：知识库里「清空学习数据」，内置方块表不会丢
· 换电脑：先导出 JSON，到新浏览器里导入

改代码 / 修 bug：
· 用 Cursor 说明现象，改完后 npm run dev 自己点几遍
· 用 Git 存档（建议），每做成一个能玩的功能提交一次

环境：
· Node 选 LTS，能玩先不要随便升级依赖
· 代码至少备份到 GitHub 或网盘，不要只留在这一台电脑

上线后：
· 免费服务器可能冷启动变慢
· 一期房间若在内存，重启即清空


九、风险（已评估，按优先级处理）

1. 问句覆盖不足 → 先保证高频问法；不会就说不确定，禁止瞎答
2. 相似方块（各种木板）→ 必须有 woodType / color 等细类
3. 「石头」误伤「圆石」→ 猜测优先精确匹配，不随便模糊包含
4. QQ 内置浏览器 → 二期再集中测，Socket.IO 预留 polling
5. 素材与名义 → 不用官方贴图，不冒充 Mojang / 网易官方
